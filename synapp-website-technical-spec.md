# SynApp Website V1 — Implementation Specification

## Purpose

This document is an implementation-ready specification for **version 1** of the SynApp marketing website. It is intended to be handed to an implementation agent so the first production-ready version can be built in one pass with minimal ambiguity.

The website is a **static Vue 3 + Vite marketing/sales site** for SynApp, a platform for managing Telegram chats, users, permissions, tagging, messaging, and automation at scale.

The site must feel modern, minimal, premium, and interactive, while keeping the first impression simple and making deeper product information easy to reach.

---

## 1. Product Positioning

### Core product idea
SynApp is an enterprise-oriented Telegram management platform that helps teams control chats, users, communication flows, and operational governance from one interface.

### Core value themes
- Centralized Telegram operations
- Bulk user and chat management
- Tagging and filtering at scale
- Messaging and communication control
- Automation and operational efficiency
- Better governance and reduced manual work

### Audience focus for V1 website
The website should primarily speak to:
- Businesses using Telegram for teams, customers, or operations
- Crypto / DeFi / Web3 teams managing large Telegram communities
- Community managers and operations teams
- Teams that need more control over Telegram than Telegram provides natively

### Messaging approach
- Enterprise-leaning, but not overly corporate
- Clear and direct, not fluffy
- Minimalist at first glance
- More detail available through deeper pages and expandable sections
- Avoid walls of text on the homepage

## 2. Website Strategy

## Why the site should be multi-page
For V1, the website should not rely on a single very long homepage. A multi-page structure is better because:

- Pricing deserves its own destination for SEO, campaigns, and direct sales links.
- Contact should have its own clear route because users expect `/contact` and sales/demo requests should not feel buried.
- The homepage should stay focused on positioning, value, and momentum instead of carrying every detail.
- Features need a dedicated deep-dive page because SynApp has enough real functionality to justify it.

### Final route structure for V1
- `/` — Homepage
- `/features` — Detailed features page
- `/pricing` — Dedicated pricing page
- `/contact` — Dedicated contact page
- `/privacy-policy` — Privacy Policy page

### Navigation
Primary header navigation should contain:
- Features
- Pricing
- Contact
- CTA button: Book a Demo

The SynApp logo in the header links to `/`.

### Footer navigation
Footer should include:
- Home
- Features
- Pricing
- Contact
- Privacy Policy

## 3. Technology Stack

### Core stack
- Vue 3
- Vite
- TypeScript
- Vue Router
- vue-i18n

### Build target
- Static site build only
- Output generated by `vite build`
- No SSR required for V1
- No custom backend in this phase

### Styling approach
- Vue Single File Components
- Global CSS tokens and base styles
- No Tailwind dependency required
- Reusable component styling through design tokens
- Mobile-first responsive CSS

### State management
No heavy state library is required. Use:
- component props
- local component state
- composables for shared behavior

### Services layer
Even though the site is static, project structure must include a services layer so integrations can be swapped later without rewriting components.

Expected service examples:
- `contactForm.service.ts`
- `seo.service.ts` or route meta helper
- `assetConfig.ts` for placeholders / URLs

## 5. Visual Direction

### Design goals
The site must feel:
- modern
- premium
- minimal
- dark and focused
- interactive in subtle ways
- polished on desktop and mobile

### Primary visual references
The user explicitly prefers modern, sleek product sites with subtle motion, polished cursor behavior, fades, and a premium interactive feel.

### Visual principles
- Minimal first impression
- Strong typography hierarchy
- Clean dark surfaces
- Limited but intentional accent color usage
- Glassmorphism only where it improves perceived quality; do not overuse it
- Motion should signal care and craft, not become distracting

### What to avoid
- Long unbroken text blocks
- Generic startup gradients everywhere
- Template-like three-card SaaS layouts repeated section after section
- Too many colors competing on one screen
- Overly loud animations
- Heavy enterprise aesthetic that feels outdated

---

## 6. Color System

Use the provided brand colors as the basis of the entire system.

| Token | Value | Usage |
|---|---|---|
| `--color-bg` | `#080B17` | Global background |
| `--color-surface` | `#10172B` | Cards, header, section panels |
| `--color-surface-2` | `#141D35` | Elevated surfaces, hover states |
| `--color-accent-blue` | `#0FA5E9` | Primary CTA, active states, links |
| `--color-accent-pink` | `#EC4799` | Secondary highlight, decorative accents |
| `--color-white` | `#FFFFFF` | Primary text |
| `--color-text-muted` | `rgba(255,255,255,0.72)` | Secondary text |
| `--color-text-faint` | `rgba(255,255,255,0.42)` | Labels, helper text |
| `--color-border` | `rgba(255,255,255,0.08)` | Borders, dividers |
| `--color-border-strong` | `rgba(255,255,255,0.14)` | Hover / active card outlines |

### Accent usage rules
- Blue is the primary functional accent.
- Pink is the secondary accent for highlights and premium emphasis.
- White text remains dominant.
- Do not make every element colorful.
- Each screen should still feel mostly dark and controlled.

## 7. Typography

### Font pairing
- Headings / display: **General Sans**
- Body / UI text: **Satoshi**

Load via Fontshare CDN.

### Type behavior
- Fluid type scale using `clamp()`
- Body text default: 16px
- Buttons and nav: 14–16px
- Strong headline hierarchy
- Keep homepage copy concise and scannable

### Tone of copy
- Short, clear, benefit-first
- Avoid buzzword-heavy marketing copy
- Product must sound competent and credible
- The homepage should feel persuasive, not overloaded

---

## 8. Layout & Interaction Style

### Core layout behavior
- Mobile-first
- Large content sections with clear breathing space
- Page width constrained for readability
- Cards and content blocks aligned on a disciplined grid
- Hero area can break the strict grid slightly for visual impact

### Glassmorphism usage
Allowed in:
- feature cards
- video placeholder frame
- pricing cards
- contact form container
- floating CTA panels

Standard glass style:

```css
background: rgba(16, 23, 43, 0.58);
backdrop-filter: blur(12px);
-webkit-backdrop-filter: blur(12px);
border: 1px solid rgba(255, 255, 255, 0.08);
box-shadow: 0 12px 40px rgba(0, 0, 0, 0.24);
```

### Motion requirements
Implement these for V1:
- smooth fade-in reveal on scroll
- subtle upward movement during reveal
- interactive hover responses on cards and buttons
- custom cursor glow on desktop
- page fade transition between routes
- reduced motion support

### Cursor effect
- Desktop only
- Soft glow following cursor with slight lag
- Blue by default, pink when hovering key interactive elements
- Must not block clicks or impair readability

## 9. SEO & Information Architecture

### SEO goals
The website should be structured to rank better than a single long scrolling page for product-intent searches.

### Required SEO setup
- Unique page title per route
- Unique meta description per route
- Open Graph tags
- Twitter card tags
- `robots.txt`
- `sitemap.xml`
- semantic heading hierarchy
- clean route names

### Translation strategy
The site should be built with `vue-i18n` from day one, but only English content is required for V1.

Reason:
- future translations become easier
- no need to refactor components later

Actual language rollout remains an owner decision.

## 10. Page Specifications

## 10.1 Homepage (`/`)

### Purpose
The homepage sells the product at a high level and moves visitors toward one of three next steps:
- explore features
- view pricing
- contact / book a demo

### Homepage sections
1. Hero
2. Problem
3. Solution overview
4. Features teaser
5. How it works
6. Pricing teaser
7. Testimonials / trust
8. FAQ
9. Final CTA

### Important homepage rule
The homepage should **not** contain the full pricing table and should **not** contain the full contact form for V1. Those belong to dedicated routes.

### 10.1.1 Hero section
Must include:
- product category label
- strong short headline
- short supporting paragraph
- primary CTA: `Book a Demo`
- secondary CTA: `See Features`
- premium video/demo placeholder area

Suggested CTA linking:
- `Book a Demo` → `/contact`
- `See Features` → `/features`

### 10.1.2 Problem section
Present Telegram management pain points in a sharp, scannable way.

Use 4–6 pain cards such as:
- manual user management
- lack of governance
- orphaned access
- moderator overload
- poor visibility
- inconsistent communication

### 10.1.3 Solution section
A simple explanation of what SynApp changes.

Should communicate:
- one control center
- easier operations at scale
- less manual work
- more structure and visibility

Include one screenshot placeholder.

### 10.1.4 Features teaser section
Show only the most important feature categories on the homepage.

Suggested feature categories:
- Bulk Operations
- Tagging & Filtering
- Messaging
- Automation Rules
- User & Chat Visibility
- Admin Control

Each card should be concise. End section with:
- `See All Features` button to `/features`

### 10.1.5 How it works
Short 3–4 step explanation.

Suggested steps:
1. Connect SynApp
2. Import chats and users
3. Organize with tags and filters
4. Operate at scale from one interface

### 10.1.6 Pricing teaser section
This section exists only to preview pricing and route users to the full pricing page.

Must contain:
- short intro
- 3 compact pricing summary cards or a compact tier strip
- `See Full Pricing` CTA linking to `/pricing`

Do not place the full comparison matrix here.

### 10.1.7 Testimonials section
Use placeholders for now, but design the section as if real proof exists.

### 10.1.8 FAQ section
Use accordion format. Keep answers concise.

### 10.1.9 Final CTA section
Large final call-to-action directing users to `/contact`.

Examples:
- `Book a Demo`
- `Talk to Our Team`

This section should be visually strong and should feel like the final conversion point of the homepage.

- Invitations

- title

## 10.3 Pricing Page (`/pricing`)

### Purpose
Provide a dedicated destination for pricing-related traffic and let sales conversations link directly to pricing.

### Structure
1. Pricing hero
2. Pricing cards
3. Feature comparison table
4. Billing / plan FAQ
5. Enterprise CTA
6. Final CTA to contact page

### Required implementation rule
All pricing content must be data-driven from a single file:
- `src/data/pricing.ts`

This includes:
- plan names
- prices
- descriptions
- feature availability
- badges
- CTA labels
- highlight state

This makes the pricing page easily configurable without rewriting components.

### Initial pricing assumptions for V1
| Plan | Indicative price | Positioning |
|---|---|---|
| Basic | $20/mo | Entry plan |
| Business | $50/mo | Stronger operational feature set |
| Business Plus | $300/mo | SSO / advanced org use |
| Business Premium | $500/mo | Higher-end business tier |
| Enterprise | Custom | Custom setup, advanced requirements |

### Important pricing notes
- No free tier for V1 website
- Enterprise must point to contact, not direct checkout
- The page should support future pricing edits with minimal effort
- The design should make it easy to hide or reorder plans later

---

## 10.4 Contact Page (`/contact`)

### Purpose
Provide a dedicated route for demo requests and sales inquiries.

### Why separate contact page is better for V1
- more conventional for users
- easier to link directly from ads, email, and sales outreach
- keeps homepage cleaner
- reduces implementation ambiguity for version 1

### Structure
1. Contact page hero
2. Contact form section
3. Optional secondary trust / response expectation block
4. Optional FAQ snippet or sales note

### Contact form fields
- Name
- Work Email
- Company
- Role (optional)
- Message

Optional field:
- Team size or number of Telegram groups

### Form behavior
- Validate client-side
- Show inline errors
- Show success state without page reload
- Include hidden honeypot field
- Abstract submit logic to service layer

### Technical integration requirement
The form component must be reusable and isolated:
- `ContactFormCard.vue`
- submit logic in `contactForm.service.ts`

For V1, it is acceptable to stub the integration, but component architecture must assume a real endpoint will be plugged in later.

## 11. Video & Screenshot Placeholder Strategy

### Video
The product demo is currently internal only. V1 should include a polished placeholder that shows where the video will live.

### Best future approach
Preferred final approach:
- create a SynApp YouTube channel or use a company-controlled YouTube account
- upload the demo there
- embed it on the site

Reason:
- easier hosting
- better streaming reliability
- easier mobile playback
- updateable without rebuilding media pipeline
- optional analytics

### Component requirement
`VideoPlaceholder.vue` must support two future modes:
- thumbnail placeholder mode
- embedded video mode

### Screenshot placeholders
The site should include explicit placeholder blocks wherever screenshots will later appear.

Each placeholder must clearly indicate what asset belongs there, for example:
- `Chat table overview screenshot`
- `User profile screen screenshot`
- `Rules page screenshot`
- `Invitations dashboard screenshot`

This helps the implementation agent build the right layout now, before final assets exist.

---

## 12. Responsiveness

### Mobile requirements
The site must feel native on phones.

Rules:
- mobile-first layouts
- no desktop squeeze-down design
- stacked content where appropriate
- large touch targets
- stable header behavior
- animations toned down on smaller screens
- cursor effect disabled on touch devices

### Expected breakpoints
- mobile base
- tablet at `768px`
- desktop at `1024px`
- wide desktop enhancements above `1280px`

### Specific mobile expectations
- Hero content stacks vertically
- Pricing cards become stacked or horizontally scrollable cards
- Tables on pricing page must remain readable on mobile, likely via horizontal scroll or card fallback
- Contact page form remains comfortable to complete on small screens

---

## 13. Accessibility

Must include:
- keyboard navigation
- visible focus states
- semantic landmarks
- one h1 per page
- proper label/input connections
- alt text for imagery
- reduced-motion behavior
- sufficient text contrast

This is required even for V1.

---

## 14. Performance Requirements

V1 should still feel fast and production-ready.

Requirements:
- lazy-load images
- font-display swap
- keep animation code lightweight
- avoid unnecessary libraries
- keep initial page payload reasonable
- no heavy visual effects that hurt low-end mobile devices

The site should look premium without becoming slow.

---

## 15. Content Rules for Implementation Agent

The implementation agent should follow these content rules while building V1:

- Use concise real marketing copy, not lorem ipsum
- Keep homepage copy intentionally brief
- Use placeholders only where assets or legal content are actually missing
- Do not invent fake testimonials as if they were real customers; label placeholder proof clearly
- Do not mention the failed partnership with PhishFort anywhere on the public website
- Do not add blog, changelog, or documentation sections in V1
- Do not add login/product app navigation to the marketing header unless specifically requested later

---

- documentation portal

- full analytics setup
- multilingual content rollout beyond English
- custom backend development
- public product video publication

## 18. Acceptance Criteria for V1

The website version 1 is considered complete when:
- all five routes exist and are navigable
- homepage is concise and polished
- pricing exists on a dedicated page
- contact form exists on a dedicated page
- features page gives meaningful product depth
- privacy policy route exists
- visual system matches the dark premium brief
- motion and cursor interactions are implemented appropriately
- site is responsive and comfortable on mobile
- pricing and contact integration are structured for later updates
- placeholder assets are clearly defined where final assets are missing

---

## 19. Summary for One-Shot Build

The implementation agent should build a **multi-page static Vue 3 website** with a premium dark aesthetic, subtle interactivity, reusable components, dedicated pricing and contact pages, and enough structure to support future content and integration updates without refactoring the whole project.

The priority is not maximum page count. The priority is a **clean, convincing, production-looking version 1** that already feels like a serious software product website.
